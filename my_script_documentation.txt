Документация по скрипту автоматической обработки проверки качества данных
(объект DQImplementation, наш скрипт my.groovy)

====================================================================
1. Что это за скрипт и когда он выполняется
====================================================================
Этот скрипт запускается автоматически при КАЖДОМ сохранении проверки качества
данных (объект DQImplementation) — ДО записи в базу. Он срабатывает:
  - при создании новой проверки;
  - при любом изменении существующей проверки;
  - при смене статуса проверки.

Скрипт делает четыре вещи:
  1) автоматически заполняет поля (автозаполнение);
  2) формирует SQL-запрос проверки для встроенных типов проверок;
  3) проверяет обязательность полей при смене статуса;
  4) управляет расписанием запуска и вспомогательными флагами.


====================================================================
2. Справочник статусов проверки
====================================================================
  "10"  — Новый / На редактировании
  "20"  — В работе
  "30"  — На согласовании
  "40"  — На проверке / Контроль заполнения
  "50"  — На подтверждении
  "60"  — Ожидает публикации
  "70"  — Опубликован
  "90"  — Новый / На редактировании
  "100" — Новый / На редактировании
  "110" — Контроль описания
  "120" — На согласовании
  "130" — На утверждении
  "140" — Утверждён
  "505" — Архитектурное ревью
  "510" — Аналитическое ревью
  "520" — Разработка
  "530" — Тестирование
  "540" — Готово к выгрузке на прод

Особую роль играют "согласующие" статусы: 50 (На подтверждении) и 70
(Опубликован). На них выполняется максимум проверок и фиксаций.


====================================================================
3. Ключевые понятия и поля
====================================================================
  standardLogic — флаг "Стандартная логика". Если true — система сама
      генерирует SQL для встроенных проверок. Если false — используется
      пользовательский скрипт. ВАЖНО: в нашем скрипте флаг только
      ВЫКЛЮЧАЕТСЯ (для отдельных типов), но нигде не включается.

  dq_type — тип проверки (см. раздел 7): notnull, unique, interval, length,
      count, gt/gteq/lt/lteq, two_fields_compare, count_compare,
      check_status, other, template, relevance.

  checking_source / checking_source2 — проверяемый источник(и) данных
      (набор данных или таблица). Источник 2 нужен для сравнений.

  checking_table / checking_table2 — физическая таблица, связанная с
      источником (заполняется автоматически).

  dbObjectLink / dbObjectLink2 — проверяемые колонки (что именно проверяем).

  dbObjectLinkPKcol — "Идентификатор записи" (первичный ключ). Нужен, чтобы
      в журнал ошибок записать, какая именно запись оказалась ошибочной.

  full_bad_records_script — SQL, который отбирает "плохие" (ошибочные)
      записи. Главный результат работы скрипта.

  full_select_script — SQL, который отбирает все проверяемые записи
      (для сверки/выборки).

  dq_period_cron — расписание запуска проверки.

  intervalStartStr / intervalFinishStr — границы диапазона (для интервала,
      длины, количества и сравнений).

  dq_type_compare — тип сравнения (для сравнения полей/количества):
      >, >=, <, <=, =, !=.


====================================================================
4. Общий порядок работы при каждом сохранении
====================================================================
Ниже — что делает скрипт по шагам при каждом сохранении, независимо от
статуса.

Шаг 1. Присвоение технического кода.
  Проверке присваивается код вида "DQ<номер>" (например DQ12345) в поля
  dq_code и code.

Шаг 2. Способ создания.
  Если поле "Способ создания" (Creation_method) пустое — проставляется
  "Ручное создание". (Если способ уже задан, ничего не меняется.)

Шаг 3. Очистка лишних полей в зависимости от выбранного типа проверки.
  При выборе типа проверки неактуальные для него поля очищаются, чтобы не
  оставалось "мусора":
    - "Проверка регламента" (check_status): выключается стандартная логика,
      границы = 50 и 100, очищаются поля второго источника.
    - "Общее" (other): выключается стандартная логика, очищаются границы
      диапазона и тип сравнения.
    - "Не NULL", "Уникальность", "По шаблону": очищаются границы диапазона
      и тип сравнения, очищаются поля второго источника.
    - "Интервал", "Длина строки", "Количество": очищается тип сравнения,
      очищаются поля второго источника.
    - "Больше"/"Больше или равно": очищается конечная граница, тип сравнения,
      поля второго источника.
    - "Меньше"/"Меньше или равно": очищается начальная граница, тип
      сравнения, поля второго источника.
    - "Сравнение полей"/"Сравнение количества": очищаются границы диапазона.

Шаг 4. Определение таблицы-источника.
  Для каждого выбранного источника определяется имя физической таблицы.
  Если источник — это файл/API/Kafka (не база данных), то проверка
  принудительно переводится в тип "Общее", стандартная логика выключается.

Шаг 5. Генерация SQL (только для стандартной логики и при изменении
  существующей проверки). См. раздел 7.

Шаг 6. Валидация обязательных полей при смене статуса. См. раздел 9.

Шаг 7. Автозаполнение полей (в зависимости от статуса). См. раздел 8.

Шаг 8. Управление расписанием. См. раздел 10.


====================================================================
5. Поведение при СОЗДАНИИ новой проверки
====================================================================
Если проверка создаётся впервые (ещё нет предыдущей версии):
  - проставляется служебный флаг shouldClose = true (признак "закрыть
    карточку" для процесса);
  - SQL для встроенных проверок НЕ генерируется (генерация работает только
    при изменении уже существующей проверки);
  - выполняется автозаполнение из Функциональных требований (см. 8.1);
  - проставляется владелец/разработчик — создатель проверки (см. 8.5);
  - для нового объекта на сервере GREENPLUM: если проверяемая таблица — это
    представление (view), выдаётся ошибка (запрет проверки представлений
    на GreenPlum).


====================================================================
6. Поведение при ИЗМЕНЕНИИ существующей проверки
====================================================================
6.1 Если проверка стандартная (standardLogic = true) и заполнен источник:
  генерируется/перегенерируется SQL проверки (см. раздел 7).

6.2 Если проверка нестандартная (standardLogic = false) или это создание:
  SQL не генерируется. В уже существующем скрипте производится замена
  текста "STATUS" на "status" (приведение регистра), и заново
  проставляются связи источника и колонок первичного ключа.

6.3 Если при смене статуса скрипт отбора "плохих" записей оказался пустым,
  а новый статус — согласующий (50 или 70), выдаётся ошибка
  "Не заполнен Скрипт отбора данных".


====================================================================
7. Типы проверок и формируемый SQL
====================================================================
Для каждого встроенного типа ниже: смысл проверки и SQL, который отбирает
"плохие" записи. Во всех примерах таблица условно обозначена как
<таблица>, проверяемая колонка — <колонка>, первичный ключ — <ключ>.
Колонки первичного ключа добавляются в выборку автоматически (чтобы было
видно, какая запись ошибочна).

7.1 "Не NULL" (notnull)
  Смысл: проверяемые колонки не должны содержать пустые (NULL) значения.
  Плохая запись — та, где любая из проверяемых колонок пустая:
    SELECT ... FROM <таблица> WHERE (<колонка1> IS NULL OR <колонка2> IS NULL ...)

7.2 "Уникальность" (unique)
  Смысл: значение (набор значений) проверяемых колонок должно быть
  уникальным. Плохие записи — дубликаты (повторяются больше одного раза).
  ВАЖНО: сейчас в этом типе есть ошибка — SQL формируется некорректно
  (подробно в отдельном файле сравнения с эталоном).

7.3 "Интервал" (interval)
  Смысл: значение проверяемой колонки должно лежать в заданном диапазоне
  [начало; конец]. Плохая запись — та, где значение ВНЕ диапазона:
    SELECT ... FROM <таблица> WHERE <колонка> NOT BETWEEN <начало> AND <конец>

7.4 "Больше"/"Меньше"/"Больше или равно"/"Меньше или равно"
  (gt / lt / gteq / lteq)
  Смысл: сравнение значения колонки с одной границей. Плохая запись — та,
  где сравнение не выполняется, например для "Больше чем":
    SELECT ... FROM <таблица> WHERE NOT (<колонка> > <граница>)

7.5 "Длина строки" (length)
  Смысл: длина текста в проверяемой колонке должна лежать в заданном
  диапазоне символов. Плохая запись — та, где длина вне диапазона:
    SELECT ... FROM <таблица>
    WHERE LENGTH(TRIM(<колонка>::text)) NOT BETWEEN <мин> AND <макс>

7.6 "Количество записей" (count)
  Смысл: общее число записей в источнике должно лежать в заданном диапазоне.
  Результат — одно число, если оно вне диапазона:
    SELECT cnt FROM (SELECT COUNT(*) AS cnt FROM <таблица>) AS c
    WHERE c.cnt NOT BETWEEN <мин> AND <макс>

7.7 "Сравнение двух полей" (two_fields_compare)
  Смысл: сравнить поле из источника 1 с полем из источника 2 по заданному
  оператору сравнения. Требуется условие объединения источников.
  Плохая запись — та, где сравнение не выполняется:
    SELECT ... <условие объединения>
    WHERE NOT (<таблица1>.<колонка1> <оператор> <таблица2>.<колонка2>)

7.8 "Сравнение количества" (count_compare)
  Смысл: сравнить количество записей источника 1 и источника 2.
  Результат — два числа (сколько в каждом), если сравнение не выполняется.

7.9 "Проверка регламента" (check_status)
  Смысл: проверка соблюдения регламента (сроков/процесса). SQL скриптом не
  генерируется — используется внешняя логика.

7.10 "Общее" (other)
  Смысл: произвольная проверка по пользовательскому скрипту. SQL не
  генерируется — пользователь пишет скрипт сам.

7.11 "По шаблону" (template)
  Смысл: проверка на основе заранее подготовленного шаблона с условием.
  В условие шаблона подставляются выбранные колонки, результат:
    SELECT ... FROM <таблица> WHERE (условие_шаблона)

7.12 "Актуальность" (relevance)
  Смысл: проверка, что данные в источнике загружены за текущую дату
  (колонка даты загрузки dm_load_ts = сегодня). Если таких записей нет —
  данные считаются неактуальными.


====================================================================
8. Автозаполнение полей (по триггерам)
====================================================================
8.1 При статусе "10" (Новый / На редактировании) — автозаполнение из
  Функциональных требований (FSD):
    - "Проверяемый источник" заполняется из поля "Таблица БД" требований;
    - "Проверяемые колонки" — из поля "Атрибут таблицы БД" требований;
    - "Идентификатор записи" (первичный ключ) — подтягивается из
      Функциональных требований: берутся колонки, отмеченные как PK
      (признак Is_pk_field). Если PK в требованиях нет — ничего не
      заполняется (без ошибки).

8.2 При переходе в статус "50" из "30"/"520"/"10" — обратное заполнение
  требований из реализации:
    - "Таблица БД" заполняется из "Проверяемой таблицы" проверки;
    - "Атрибут таблицы БД" — из "Проверяемых колонок".
  (Нужно, чтобы к моменту подтверждения требования были синхронизированы
  с фактической реализацией.)

8.3 Автозаполнение первичного ключа (общее):
  Если "Идентификатор записи" не заполнен — система сама находит в таблице
  колонки с признаком первичного ключа (is_primary_key) и подставляет их.

8.4 Автозаполнение "Описания ошибки":
  Если у проверки привязано бизнес-правило, а "Описание ошибки" пустое —
  оно копируется из бизнес-правила.

8.5 При статусе "10" — владелец и разработчик:
  Если владелец (owner) и разработчик (tech_owner) не заполнены — в оба
  поля подставляется пользователь, создавший проверку.


====================================================================
9. Обязательные поля по статусам
====================================================================
При СМЕНЕ статуса проверяется заполненность полей. Если поле пустое и
проверка переходит в указанный статус — выдаётся ошибка (сохранить
нельзя).

  Поле                               | Обязательно при переходе в статус
  -----------------------------------+-----------------------------------
  Бизнес-правила КД (linkedBusinessRule) | 30, 520, 50, 70
  Описание ошибки (dq_error_text)    | 30, 520, 50, 70
  Проверяемый источник (checking_source) | 50, 70
  Заказчик проверки (owner)          | 30, 520, 50, 70
  Разработчик проверки (tech_owner)  | 30, 520, 50, 70
  Команда заказчика (BrdTeam1)       | 520, 50, 70
  Команда разработчика (BrdTeam2)    | 520, 50, 70
  Тип проверки (dq_type)             | 50, 70
  Downstream-проверка (downstream_impl) | 50 (если заполнен downstream_rec_id)
  Идентификатор записи Downstream (downstream_rec_id) | 50 (если заполнена downstream_impl)

Дополнительные проверки при согласующих статусах (50, 70):
  - Если заказчик != разработчик — обязательно заполнена "Таблица БД".
  - Должно быть заполнено "Расписание запуска проверки" (dq_period_cron),
    кроме случаев, когда проверка "после обновления" (UpdateRun) или
    приостановлена (paused).
  - Должен быть заполнен "Идентификатор записи" (первичный ключ) — иначе
    ошибка "Не указан Идентификатор записи".


====================================================================
10. Дополнительные бизнес-правила
====================================================================
10.1 Расписание запуска (dq_run_type):
  - если тип запуска "Приостановлена" (paused) — расписание очищается;
  - если тип запуска "После обновления" (after_update) — расписание
    очищается и ставится флаг UpdateRun = true;
  - если тип запуска обычный и UpdateRun не установлен — UpdateRun = false.

10.2 При статусе "50" — контроль запусков:
  Если проверка создана вручную (способ создания != "Автоматическая
  генерация") и переводится в статус "50", выполняется проверка статистики
  запусков (таблица dq.dqimplementation_stat):
    - если проверка ещё ни разу не запускалась — ошибка;
    - если последний запуск не успешный — ошибка;
    - если последняя версия скрипта ещё не запускалась (скрипт менялся
      позже последнего запуска) — ошибка.

10.3 Фиксация даты проверки:
  Если при сохранении изменился SQL (скрипт отбора или выборки) — в поле
  dateValidation записывается текущее время. (Используется далее для
  контроля "запускалась ли последняя версия скрипта".)

10.4 Для типа "Актуальность" (relevance):
  Расписание запуска выставляется автоматически на час, указанный в
  Функциональных требованиях (поле DataTime). Если расписание уже задано —
  не перезаписывается.

10.5 Запрет представлений на GreenPlum (для новых проверок):
  Если источник на сервере GREENPLUM и таблица является представлением
  (view) — проверка запрещена (ошибка) из-за высокой нагрузки.

10.6 Копирование скрипта в скрипт автозакрытия:
  При переходе в согласующий статус (50/70) скрипт отбора "плохих" записей
  копируется в поле filter_script (если оно пустое).


====================================================================
11. Важное примечание про "Стандартную логику"
====================================================================
Флаг standardLogic решает, будет ли скрипт генерировать SQL для встроенных
проверок. В НАШЕМ скрипте этот флаг только ВЫКЛЮЧАЕТСЯ (для типов
"Проверка регламента", "Общее" и источников-файлов/API/Kafka), но нигде не
ВКЛЮЧАЕТСЯ. Это значит, что включение стандартной логики должно происходить
вне этого скрипта (в интерфейсе при выборе встроенной функции или в
настройках поля). Если флаг не включён — SQL для встроенных проверок не
генерируется. Этот момент стоит проверить отдельно.
