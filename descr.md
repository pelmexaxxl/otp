# Синхронизация FSD ↔ DQImplementation / DQLA

Когда на карточке FSD нажимают кнопку, скрипт проверяет: есть ли для этого набора уже созданные Проверка КД и DQLA. Если есть — подтягивает в них актуальные данные из FSD (например, если на FSD поменялся технический владелец или список первичных ключей). Если нет — создаёт.

## Логика поиска

### Проверка КД (DQImplementation)

Ищется по имени в папке <id>. Имя формируется строго: <схема>.<код_набора>: Проверка на уникальность первичного ключа

Если нашли — работаем с ней. Если нет — считаем, что Проверки КД ещё нет.

### DQLA

Ищется по имени в папке <id>. Логика двухступенчатая:

    1. Сначала без суффикса — ищем DQLA с именем = <схема> (в нижнем регистре).

    2. Проверяем совпадение владельца. Если у найденного DQLA поле representer (Поставщик данных) совпадает с полем techowner (Технический владелец) на FSD — DQLA нашёлся, работаем с ним.

    3. Если не совпало — берём Agile-команду технического владельца (fsdTeam) и ищем DQLA с именем <схема>: <команда>. Если нашли — работаем с ним. Если нет — DQLA для этого владельца ещё не создан.

==Важно!== У одной схемы может быть несколько DQLA — по одной на каждую Agile-команду. Суффикс : <команда> различает их.

## Что синхронизируется

### В Проверке КД (DQImplementation)

Обновляются три поля — список первичных ключей таблицы:

    dbObjectLink — проверяемый объект данных

    dbObjectLinkReq — то же самое, требование к проверке

    dbObjectLinkPKcol — идентификатор записи (PK-колонки)

Список PK-колонок берётся с FSD: проход по атрибутам таблицы (tableAttr), отбираются те, у которых Is_pk_field = true. По каждой колонке находится соответствующая колонка в физической таблице БД (по имени в верхнем регистре).

Обновление происходит только если данные реально изменились — если список PK на FSD тот же, что и в Проверке КД, никакой записи не производится.

### В DQLA

Обновляются два поля из FSD:

    representer (Поставщик данных) — из поля techowner на FSD

    business_steward (Технический стюард данных) — из поля analyst на FSD

Только если отличаются от текущих значений в DQLA. Если на FSD поле пустое — оно не затирает существующее значение в DQLA.

## Что НЕ делает синхронизация

- Не трогает создание — если объекта нет, синхронизация просто ничего не делает и сообщает main'у, что объекта нет.

- Не трогает названия объектов — имя DQLA/Проверки КД при синхронизации не меняется.

- Не трогает родителя (parent) — папка, в которой лежит объект, не меняется.

- Не трогает индикатор (DQIndicator) — он синхронизируется отдельно (или не синхронизируется).

## Что происходит при потере владельца DQLA

Если DQLA найден по имени, но techowner на FSD не совпадает с representer в DQLA:

    Скрипт пробует найти DQLA с суффиксом команды технического владельца.

    Если находит — синхронизирует его.

    Если не находит — считает, что DQLA для текущего владельца нет, и main создаст новый DQLA с суффиксом : <команда>.

Это означает: смена технического владельца на FSD приводит к созданию нового DQLA под новую команду. Старый DQLA остаётся в системе нетронутым.

## Что еще важно (может быть)

    1. Синхронизация не удаляет объекты. Если DQLA больше не нужен (например, владелец сменился) — он останется в системе. Удаление — ручная операция.
    
    2. Смена технического владельца на FSD = новый DQLA. Это by design — каждый DQLA привязан к Agile-команде.
    
    3. Список PK в Проверке КД всегда приводится к текущему состоянию FSD. Если на FSD добавили/убрали PK-колонку — Проверка КД обновится.
    
    4. Данные не перезаписываются, если не изменились. Лишних обновлений не будет.
    
    5. Если объект не найден — синхронизация не падает. Она просто сообщает main'у, что объекта нет, и main идёт по ветке создания.
    
    6. Ошибка поиска таблицы в БД (например, неверно указан сервер/каталог/схема на FSD) — синхронизация выбрасывает ошибку, и процесс останавливается.

## Чего в синхронизации нет (по сравнению со старой версией)

Раньше на FSD хранились поля ImplId и DQLAId — id-ссылки на Проверку КД и DQLA. Сейчас их нет:

    Синхронизация не читает эти поля.

    Синхронизация не пишет эти поля.

    Поиск объектов идёт только по имени — это единственный источник правды.

Это упрощает логику и убирает целый класс ошибок (устаревшие id, рассинхрон id и имени).
