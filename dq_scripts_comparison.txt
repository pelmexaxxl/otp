Сравнение генерации SQL-скриптов проверок качества данных
(наша реализация vs эталон Adastra)

====================================================================
Что сравнивали
====================================================================
Два скрипта, которые автоматически формируют SQL-запрос проверки качества
данных при сохранении проверки (объект DQImplementation):
  - adastra.groovy — эталонная логика (как должно быть);
  - my.groovy     — наша реализация.

Сравнивалась только та часть, которая формирует SQL, а также флаг
"стандартная логика", который решает, будет ли SQL генерироваться вообще.
Ниже — все найденные расхождения.


====================================================================
1. ГЛАВНАЯ ПРОБЛЕМА — проверка «Уникальность»
====================================================================
Проверка «Уникальность» должна находить записи, где значение (или набор
значений) проверяемых колонок повторяется больше одного раза.

Пример: таблица dqstage.stg_customers,
  - проверяем уникальность по колонкам phone и email,
  - первичный ключ (Идентификатор записи) — customer_id.

КАК ДОЛЖНО БЫТЬ (эталон):

    SELECT phone, email,
           COUNT(*) AS cnt,
           string_agg(customer_id::text, ',') AS customer_id
    FROM dqstage.stg_customers
    GROUP BY phone, email
    HAVING COUNT(*) > 1

Смысл: группируем записи по проверяемым колонкам, оставляем группы, где
записей больше одной (дубликаты), и собираем в одну строку через запятую
все customer_id, которые "схлопнулись" в этот дубль.

КАК ФОРМИРУЕТСЯ СЕЙЧАС (наша реализация):

    SELECT phone, email,
           COUNT(*) AS cnt,
           customer_id AS pk_list
    FROM dqstage.stg_customers
    GROUP BY phone, email
    HAVING COUNT(*) > 1

ПОЧЕМУ ЭТО НЕПРАВИЛЬНО
Колонка customer_id попала в SELECT "как есть": она не входит в GROUP BY
и не обёрнута ни в какую агрегатную функцию. База данных не сможет
выполнить такой запрос и вернёт ошибку вида:

    column "customer_id" must appear in the GROUP BY clause
    or be used in an aggregate function

То есть проверка «Уникальность» в текущем виде не просто считает неверно —
она вообще не выполняется (падает с ошибкой).

ПРИЧИНА (для понимания)
В коде было выражение, которое оборачивает список первичных ключей в
агрегатную функцию string_agg(...). При доработке эта обёртка была удалена
(в коде остался комментарий "было"/"стало"). Вместо "собрать ключи в строку
через запятую" код теперь просто подставляет колонку ключа без агрегации.

Дополнительно: даже если вернуть string_agg, нужно вернуть приведение к
тексту (::text), иначе для числовых ключей будет ошибка типов.

ЧТО ДОЛЖНО БЫТЬ ДЛЯ СОСТАВНОГО КЛЮЧА
Если первичный ключ состоит из нескольких колонок (например customer_id
и order_id):

    ... string_agg(customer_id::text || '|' || order_id::text, ',') AS pk_list ...


====================================================================
2. ВАЖНО — управление флагом «Стандартная логика» (standardLogic)
====================================================================
ЧТО ЭТО ЗА ФЛАГ
standardLogic (в интерфейсе — «Стандартный скрипт» / «Стандартная логика»)
определяет, будет ли система САМА генерировать SQL для встроенных проверок
(Уникальность, Не NULL, Интервал, Больше/Меньше, Длина, Количество и т.д.),
или скрипт задаётся пользователем вручную.

  - true  = генерировать SQL автоматически (стандартная логика);
  - false = не генерировать, использовать пользовательский скрипт.

КАК ФЛАГОМ УПРАВЛЯЕТ ЭТАЛОН
  1. При создании новой проверки флаг принудительно ставится в true
     (стандартная логика включена по умолчанию).
  2. Затем флаг выключается (false) только в трёх случаях:
       - тип «Проверка регламента» (check_status);
       - тип «Общее» (other);
       - источник данных — файл / API / Kafka (не база данных).
  3. Генерация SQL запускается только если флаг остался true.

КАК ФЛАГОМ УПРАВЛЯЕТ НАША РЕАЛИЗАЦИЯ
  1. При создании новой проверки флаг НЕ ставится в true — эта строка
     закомментирована. Вместо неё ставится другой флаг shouldClose.
  2. Функция AutocomleteBool(), которая должна включать стандартную логику
     при выборе встроенной проверки, тоже закомментирована.
  3. Итого: в этом скрипте флаг только ВЫКЛЮЧАЕТСЯ (в тех же трёх случаях),
     но нигде не включается.

ЧЕМ ЭТО ГРОЗИТ
  - В эталоне встроенные проверки гарантированно попадают в генератор SQL,
    потому что флаг включён с момента создания.
  - В нашей версии ничто в этом скрипте не включает флаг — он должен быть
    установлен извне (интерфейс или значение поля по умолчанию). Если
    внешний механизм его не ставит, то встроенные проверки (включая
    «Уникальность») вообще не генерируют SQL и обрабатываются как
    «нестандартные».

  Это важно и для п.1 («Уникальность»): ошибка с агрегацией ключей
  проявится только если флаг true и генерация реально запускается. Сначала
  нужно убедиться, что флаг вообще включается.

ЧТО ПРОВЕРИТЬ
Где и когда стандартная логика (standardLogic) ставится в true: в настройках
поля по умолчанию, в интерфейсе при выборе встроенной функции или в другом
скрипте.


====================================================================
3. Прочие расхождения (влияют на SQL)
====================================================================

3.1 Проверка «Не NULL» (notnull) — разный набор колонок
--------------------------------------------------------------------
  - Эталон проверяет ТОЛЬКО ПЕРВУЮ выбранную колонку:
        WHERE c1 IS NULL

  - Наша проверяет ВСЕ выбранные колонки (любая из них NULL = "плохая"):
        WHERE (c1 IS NULL OR c2 IS NULL OR ...)

По сути наша логика правильнее (если выбрано несколько колонок — проверять
надо все), но это расхождение с эталоном. Нужно зафиксировать, какое
поведение считать верным.

3.2 Проверка «По шаблону» (template) — ИНВЕРТИРОВАНО условие
--------------------------------------------------------------------
Второе по важности расхождение после «Уникальности».

  - Эталон формирует:
        ... WHERE NOT (условие_шаблона)
    то есть "плохая" запись — та, где условие шаблона НЕ выполняется.
    Шаблон описывает корректное состояние записи.

  - Наша формирует:
        ... WHERE (условие_шаблона)
    то есть "плохая" запись — та, где условие выполняется.

Это ПРОТИВОПОЛОЖНАЯ логика: проверка будет помечать как ошибочные ровно те
записи, которые на самом деле корректны (и наоборот).

Дополнительно, в нашей версии два вида шаблонов:

  1) «Образец реализации» (DQImplSample) — берётся поле filter_condition2.
     По названию это, вероятно, "условие-фильтр" (то, что отбирает плохие
     записи), поэтому для него WHERE (условие) может быть корректным.

  2) Обычный шаблон — берётся то же поле template_script, что и в эталоне,
     но у нас тоже WHERE (условие) без NOT.

Вывод: ветка обычного шаблона (template_script) перевёрнута относительно
эталона. Нужно уточнить у авторов шаблонов, что означает template_script —
"условие корректности" или "условие ошибки". Сейчас по коду — расхождение
с эталоном.

3.3 Дополнительный псевдоним «checked_» у колонок в SELECT
--------------------------------------------------------------------
В списке выборки (SELECT) наша реализация добавляет псевдоним вида
checked_имя_колонки к колонкам, которые одновременно являются первичным
ключом и проверяемой колонкой:

    SELECT customer_id, phone AS checked_phone, ...

Эталон таких псевдонимов не добавляет. Влияет на названия колонок в
результате. Если последующая обработка (журнал ошибок, отчёты) ориентируется
на имена колонок — это может быть важно.

3.4 Определение колонок первичного ключа — разные атрибуты
--------------------------------------------------------------------
Чтобы понять, какие колонки составляют «Идентификатор записи» (первичный
ключ), эталон смотрит признак колонки memberPK, а наша реализация —
is_primary_key.

Если в справочнике колонок признак называется иначе, чем is_primary_key, то
«Идентификатор записи» будет заполняться неверно (или пусто), а значит
неверно сформируется и SQL — особенно для «Уникальности», где ключи
агрегируются.

3.5 Приведение ключей к тексту (::text)
--------------------------------------------------------------------
Эталон приводит значения ключей к тексту при агрегации
(string_agg(ключ::text, ...)). В нашей реализации это приведение убрано.
Для текстовых ключей неважно, для числовых/дат — вызовет ошибку типов.
Актуально в связке с п.1 («Уникальность»).


====================================================================
4. Что совпадает (проверено, расхождений нет)
====================================================================
Следующие проверки формируют одинаковый по смыслу SQL (мелкие отличия в
пробелах/регистре на результат не влияют):
  - Интервал (interval)
  - Больше / Меньше / Больше или равно / Меньше или равно (gt/lt/gteq/lteq)
  - Длина строки (length)
  - Количество записей (count)
  - Сравнение количества (count_compare)
  - Сравнение двух полей (two_fields_compare)

Управление флагом «Стандартная логика» в части ВЫКЛЮЧЕНИЯ совпадает:
обе версии выключают его для «Проверки регламента», «Общего» и для
источников-файлов/API/Kafka.


====================================================================
5. Прочее (не влияет на сам SQL, но на поведение)
====================================================================
  - В нашей версии появился новый тип проверки «Актуальность» (relevance),
    которого нет в эталоне. Это осознанное добавление, не расхождение.
  - Ошибка "Не указан Идентификатор записи": в эталоне выдаётся всегда,
    в нашей версии — только на согласующих статусах. Влияет на то, на каком
    шаге пользователь узнаёт о незаполненном первичном ключе.


====================================================================
6. Итог
====================================================================
Что обязательно исправить / проверить:
  1. «Уникальность» — вернуть агрегацию первичных ключей (string_agg)
     и приведение к тексту (::text). Без этого проверка падает с ошибкой.
  2. «По шаблону» (обычный шаблон template_script) — разобраться с
     инверсией условия (NOT). Сейчас логика противоположна эталону.
  3. Флаг «Стандартная логика» — убедиться, что он включается (standardLogic
     = true) при выборе встроенной функции. В нашей версии внутри скрипта
     он только выключается и нигде не включается.

Что нужно решить (расхождения без падения, но требующие выбора верного
поведения):
  - не NULL: проверять одну колонку или все;
  - псевдонимы checked_;
  - признак первичного ключа: memberPK или is_primary_key;
  - приведение к тексту ::text.
